Security model

What protects what, which secret opens which door, and where the protection stops.

There are four kinds of secret, and none works as another. Every parcel (a request) is checked twice: at the desk (the Hub) and again on the laptop. The laptop never accepts a connection from outside. The limits are real, and they are listed at the end of this page.

Who talks to whom

Four parties are involved. Each line between them carries one kind of secret. Read the picture from the outside in.

The secrets are long random strings (32 characters after the prefix). That is why a plain SHA-256 hash is enough to store them. The Hub never keeps the original, so it cannot show one again.

Two checks, not one

A contract says what one key may do: which folders, which tasks, how many parcels a day, when it expires, and which tasks wait for you. The rule that applies it lives in one shared file. Both sides run it.

  1. The Hub checks first. A parcel that breaks the contract is refused, recorded, and never sent to the laptop. The Hub checks again just before it hands a queued parcel over.

  2. The laptop checks again before it does anything. The Hub sends the contract inside every job, and the laptop checks that contract again. This catches real-path tricks only the laptop can see, and Hub bugs or stale state. If you set a laptop policy (~/.mailroom/policy.json, managed with mailroom policy), the daemon also refuses any contract wider than it, so a compromised Hub cannot widen what the laptop does. With no policy file the daemon trusts the contract the Hub sends and logs a warning once.

The second check also catches tricks that text alone hides. The laptop expands ~ with its own home folder and checks expiry and the task list with its own clock. Say a contract allows ~/projects.

  • Dot-dot: ~/projects/../.ssh/key is tidied to ~/.ssh/key, which is outside the folder, so it is refused. Both the Hub and the laptop catch this one.
  • Symlink: a symlink is a file that points somewhere else. ~/projects/shortcut may look inside the folder but point at /etc. The Hub only sees the text. The laptop resolves the real path first, sees /etc, and refuses. Only the laptop can catch this one.

make a contract for one folder, then send a read_file parcel with a path like ~/that-folder/../other. The parcel is refused and the Events page shows why.

What protects what

ProtectionWhat it does
Constant-time comparisonKeys, credentials and the password are compared in a way that takes the same time whether they are close or not. A wrong or wrong-kind token costs the same as a wrong one.
Origin check on writesA POST, PUT or DELETE to an owner route is refused (403 bad_origin) if its Origin header names another site. This stops another web page from using your signed-in browser. Reads are not checked, so the browser extension can read.
Session cookie flagsHttpOnly (scripts cannot read it), SameSite=Strict (not sent from other sites) and Secure (HTTPS only; the one exception is localhost for development).
Login limiter5 wrong passwords per 15 minutes per IP address. After that, sign-in answers 429 with the seconds to wait.
Sign-in gateThe Worker answers every request before any file is served (run_worker_first). Without a session you get only the sign-in page and its own files. This includes these docs.
Size and rate limitsClient API: body up to 256 KB, 60 requests a minute per key. MCP: body up to 64 KB, 120 requests a minute per token. Files the laptop reads or writes: up to 200 KB. A claude task has a 5 minute timeout and its output is cut at 200 KB.
Daily limitEach contract caps parcels per key per UTC day: two keys on one contract each get the full limit. Cancelled parcels count; refused ones do not. The Hub counts them, not the client.
No inbound connectionThe daemon only dials out. It runs no server, so there is nothing to attack from the internet.

What is logged, and what is not

Logged: every state change, as an event: who (job events carry the key id; only key, token and MCP-call events carry a label), what task, the parcel id, and the refusal reason when there is one. The log only grows and cannot be edited.

Never logged: keys, tokens, daemon credentials, the owner password, session values, or file contents.

One thing is stored but not logged. A parcel's arguments and result (for example the text of a file a client asked to read) are kept with the parcel in the Hub database, so you can see what happened. Treat the Hub as holding that content. A refusal reason can also quote a path.

Limits and risks

This is the honest part. None of it is alarming, but you should know it.

  • A contract limits where and which task. It does not limit what claude does inside the folder. The claude task runs Claude Code on your laptop in the folder you allowed, with a prompt the sender wrote. Allow it only to keys you trust, keep the folder narrow, and put claude in the approval list so you read the prompt first.
  • An approve token is power. Whoever holds one can release any risky step. See Claude and other apps.
  • The owner password is the root of trust. Anyone who has it can do everything: make keys, tokens and contracts. Make it long and unique. A stolen session cookie works until it expires (7 days) or you change SESSION_SECRET.
  • The sign-in page is public. Anyone on the internet can reach it. The limiter slows guessing per IP address, not across many addresses, so password strength matters.
  • One owner only. There are no users, roles or separate logins.
  • No third-party audit. The code has its own tests, but nobody outside has reviewed it.
  • The interface was tested with simulated users only. They were small Claude models, two runs per task. Treat that as a signal, not proof.
  • Without a laptop policy, the laptop trusts the Hub for what a contract says. The Hub sends the contract, so a compromised Hub could send a wider one. Set a ceiling with mailroom policy allow-folder, allow-task, allow-command, allow-claude-tool and claude-max-turns; the daemon then refuses anything beyond it. The policy does not yet cap file size.
  • Your laptop is in the loop. The second check does not protect you from someone who already controls the laptop itself.
