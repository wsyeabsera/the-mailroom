The laptop and the daemon

Your laptop is where the real work happens, and a small program called the daemon is what lets it receive parcels without opening a single door to the internet.

The daemon is a small program you start with mailroom run. It phones the Hub, keeps the line open, and waits for work. Before it does anything it checks the contract again. If the laptop is away, parcels queue at the desk and run in order when it comes back.

What the daemon is

In the mailroom picture, the desk is the Hub in the cloud and the laptop is the back room where parcels are opened. The daemon is the clerk in that back room. It does three things:

  • It connects to the Hub with its own secret, the daemon credential (it starts with mrd_). This is not a client key. A client key never works as a daemon credential.
  • It receives jobs from the Hub, one at a time.
  • It checks each job again, does it, and sends back the result.

Why it dials out

The laptop opens the connection to the Hub. The Hub never opens one to the laptop. So your laptop needs no public address, no open port and no router settings. Nothing on the internet can start a conversation with it.

Under the hood

The connection is a WebSocket to /daemon on the Hub. The daemon sends its credential in an Authorization header. If the line drops, the daemon reconnects after about 1 second, then waits longer each time (up to about 30 seconds). The Hub pings the daemon every 25 seconds. If it hears nothing for 60 seconds, it treats the laptop as gone. Only one daemon can be connected at a time: a second valid connection replaces the first. So if you run the background service and also a manual mailroom run, they take over from each other: the one that loses exits with code 2, and launchd restarts the service about 30 seconds later.

When the laptop is away

Laptop asleep, lid closed, or no network? The Hub notices and the app says out to lunch. New parcels that the contract allows are not lost. They wait at the desk in the order they arrived. When the daemon reconnects, the Hub sends them one by one, oldest first.

You can see this in the app. The Overview and Laptop pages show a banner, the time the laptop was last seen, and the list of parcels in the queue. The rail at the bottom left says "Laptop away".

  • If the laptop drops while a job is running, the Hub puts that job back in the queue and the daemon stops it. It runs again after the reconnect.
  • If you revoke the key that sent a parcel, its queued, waiting and running parcels are cancelled. If you edit the contract, queued parcels are checked again just before the Hub sends them.
  • Parcels that wait for your approval are held at the Hub and are not affected by the laptop being away. You can approve them while it is out. They run when it returns.

The daemon checks again

The Hub checks every parcel against its contract before sending it. The daemon checks again. It runs the same contract check itself. The Hub sends the contract inside every job, and the daemon checks that one. On top of that, the laptop can keep its own ceiling in ~/.mailroom/policy.json (folders, tasks and optional command names, file mode 0600). The daemon reads it fresh for every job and refuses any job whose contract goes beyond it, so a compromised Hub cannot widen what the laptop will do. Set it with mailroom policy show, mailroom policy allow-folder <path> and mailroom policy allow-task <task>. If the file does not exist, the daemon has no ceiling, trusts the Hub's contract and logs a warning once. An unreadable or malformed policy file refuses every job.

The daemon also does one thing the Hub cannot: it asks the real disk where a path ends up. It expands ~ with the laptop's own home folder, cleans up .., then follows every symlink on the way (a symlink is a file that points somewhere else). If the real location is outside the contract's folders, the job is refused and nothing is read or written.

A refusal from the daemon shows up on the parcel as refused with the reason "<path> resolves outside the contract folders". The parcel page then compares what was asked with what the contract allows.

The daemon does not count the daily limit. Only the Hub counts parcels per day. The daemon re-checks the expiry, the allowed tasks and the folders.

The four tasks

A task is the kind of work a parcel asks for. The laptop knows exactly four. The daemon runs one job at a time.

TaskWhat it doesLimits
echoSends your text straight back. Use it to test the whole route.None.
read_fileReads one file and returns its text.The path must be a file inside a contract folder. Larger than 2 MB: the job fails with "file is bigger than 2 MB". A result over 200 KB is kept by the Hub for 7 days.
write_fileWrites the given text to a file. It makes missing folders inside the allowed folder. It writes to a temporary file first, then renames it into place.Content over 200 KB fails. You choose per contract which tasks wait for your approval.
claudeRuns claude -p "<prompt>" in a folder (cwd) the contract allows and returns what it prints.5 minute timeout, then it is stopped and the job fails with "claude timed out". Only the first 2 MB of output is kept. Needs claude on the daemon's PATH.

A claude task runs with whatever permissions claude -p has on that machine. The contract limits which folder it starts in. It does not limit what Claude does inside it. Keep claude out of contracts you do not trust.

Under the hood: changing the 5 minutes

The timeout is 5 minutes unless the environment variable MAILROOM_CLAUDE_TIMEOUT_MS is set to a number of milliseconds. Set it in the shell that starts mailroom run. The background service does not pass your shell's variables on, and mailroom service install writes its definition afresh each time, so treat this as a setting for mailroom run in a terminal.

If the credential is rotated

Rotating the credential (Laptop page, "Rotate credential") kills the old one at once. This is the move to make if you think the credential leaked. The Hub closes the daemon's connection. The daemon prints "The daemon credential was rotated. Run mailroom login with the new credential." and exits. It does not retry, because retrying cannot work.

  1. In the app, open Laptop and rotate. Copy the new credential. It is shown once.

  2. On the laptop run mailroom login and paste it at the hidden prompt.

  3. If you use the background service, run mailroom service install again. It replaces the running copy at once. Otherwise start mailroom run.

  4. Check with mailroom service status. The queued parcels then run.

Keep it running in the background

Running mailroom run in a terminal stops when you close it. On macOS, let the system do it for you:

mailroom login               # once: Hub URL and credential
mailroom service install     # start now, and at every login
mailroom service status      # installed? running? does the Hub accept it?
mailroom service uninstall   # remove it

service install sets up a launchd user agent. launchd is the macOS program that starts and watches background jobs. It creates two things and nothing else:

WhatWhere
The service definition~/Library/LaunchAgents/dev.mailroom.daemon.plist
The log (output and errors)~/Library/Logs/mailroom-daemon.log
  • It starts when you log in to your Mac (not before), and launchd starts it again if it stops. If it exits repeatedly, launchd waits 30 seconds between tries.
  • It holds no secret. The credential stays in ~/.mailroom/config.json, readable only by you. The service definition holds the command, a PATH and your home folder.
  • The PATH it gives the daemon contains Node's folder, ~/.local/bin, /opt/homebrew/bin, /usr/local/bin and the system folders. launchd normally gives programs almost no PATH, and the claude task needs to find claude.

The log is plain text. A start and one reconnect look like this (the number in brackets is a connection close code, so yours may differ):

mailroom daemon -> https://<your-hub>
connected to the Hub
disconnected (1006); reconnecting in 1.1s
connected to the Hub

mailroom service works on macOS only. On Linux or Windows, run mailroom run under your own supervisor (systemd, for example).

mailroom status and mailroom service status ask the Hub a read-only question: does it accept my credential, and is a laptop connected? They never connect as a daemon, so they are safe to run while the daemon is working. A Hub older than v0.3.3 has no such check, and status says so instead of guessing: redeploy the Hub.
