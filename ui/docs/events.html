Events

The Mailroom's logbook: one line for everything that happens, in order, never changed afterwards.

Each time something changes (a parcel arrives, a key is made, the laptop connects) the Hub adds one event to the log. Each event has a number, seq, that only goes up. You can read the log, replay what you missed with ?after=<seq>, or watch it live. There are 18 kinds of event. None of them holds a secret.

What the log is

Think of the mailroom logbook on the desk. Staff write a line for each thing that happens and never rub one out. The event log works the same way. It is append-only: new events go on the end, and old ones are never edited or removed.

That is useful. When something looks wrong, the log tells you what happened and in what order, and nobody can quietly tidy it up afterwards.

The shape of an event

{
  "seq": 41,
  "ts": 1767225600000,
  "kind": "job.done",
  "payload": {"job_id":"p_1000","key_id":"k_1000","task":"echo"}
}

seq is the number. ts is the time, in milliseconds since 1970. kind says what happened. payload holds the details.

Every kind of event

Parcels

All parcel events carry job_id, key_id and task. Some add reason. They carry the key's id, not its label. Only the key, token and MCP events below carry labels (key.*, token.* and mcp.call).

KindIn plain wordsExtra field
job.queuedA parcel was accepted and is waiting for the laptop. It also appears when a parcel goes back in the queue because the laptop dropped.reason on a requeue
job.waiting_approvalA parcel is allowed but waits for your yes.
job.refusedA parcel was turned away by the contract or by the laptop's own check.reason
job.approvedYou (or an approve token) said yes. It goes back to the queue.
job.declinedYou (or an approve token) said no.reason
job.runningThe Hub sent the parcel to the laptop.
job.doneThe laptop finished it.
job.failedThe laptop tried and it failed.reason
job.cancelledThe parcel's key was revoked, so it was stopped.reason

A normal parcel that needs no approval leaves this trail: job.queued, job.running, job.done. One that needs approval leaves job.waiting_approval, job.approved, job.running, job.done.

Who reads the log

  • The Events page in the web app loads the latest 100 events when you open it, newest at the top, then opens the live stream from there. Older events are not on that page. If the stream drops, it tells you ("Lost the line"), counts what you missed, and a Catch up button fetches it.
  • The browser extension shows the latest 5 events from the overview, not the full log.
  • Claude can read it with the mailroom_events tool (see Claude and other apps).

Replay and live

Every reader remembers the last seq it saw. To catch up, it asks for everything after that number. These are owner routes, so they need your session cookie.

curl "https://<your-hub>/admin/events?after=38&limit=200" \
  -b "mr_session=..."

{"events":[
  {"seq":39,"ts":1767225540000,"kind":"key.created","payload":{"key_id":"k_1001","label":"notes-bot"}},
  {"seq":40,"ts":1767225580000,"kind":"job.running","payload":{"job_id":"p_1000","key_id":"k_1000","task":"echo"}}
 ],
 "last_seq":40}

last_seq is the newest number in the whole log, so you can tell if there is more. The default limit is 200 and the most you can ask for is 1000. Without tail you get the first limit events after after, which suits replay and catch-up. Add &tail=1 to get the last limit events instead (still oldest first), which suits a first load: the Events page asks for ?limit=100&tail=1.

To watch live, open the stream. It replays everything after after first, then stays open and sends each new event. A : ping line arrives every 20 seconds as a heartbeat.

curl -N "https://<your-hub>/admin/events/stream?after=40" \
  -b "mr_session=..."

: open

id: 41
data: {"seq":41,"ts":1767225600000,"kind":"job.done","payload":{...}}

Use -N so curl prints each event as it arrives. Open the Events page next to it, then send an echo parcel and watch both.

What is never in the log

Keys, admin tokens, daemon credentials, the owner password and session values are never written to an event. Neither are file contents or a parcel's arguments and result. Events carry ids, labels, task names and short reasons only.

A reason can quote text. A refusal such as "~/secret/a.txt is outside the contract" contains the path, and a failure may contain a short error message from the laptop. Do not put secrets in file names.

The parcel itself (its arguments and result) is stored in the Hub database. See Security model. For the routes in one table, see the HTTP API.
