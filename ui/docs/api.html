HTTP API

Every route the Hub answers, who may call it, and what comes back.

There are three audiences and one extra door. Clients (apps) send parcels with a key. The owner (you, in a browser) manages everything with a session cookie. The daemon (your laptop) holds a WebSocket open. Claude and other MCP apps use /mcp, described in Claude and other apps. Everything is JSON over HTTPS, and errors always look like {"error":"<code>"}.

The doors into the Hub

How to read the tables

Times are milliseconds since 1970 (created_at, ts). Ids look like p_1000 (parcel), k_1000 (key), c_1000 (contract) and t_1000 (token). Unknown routes answer 404 not_found and a wrong method answers 405 method_not_allowed. A body that is not a JSON object is 422 invalid.

Client API

Header: Authorization: Bearer mr_live_.... A key that is unknown, revoked or whose contract has expired gets 401 bad_key. Limits: body 256 KB (413 too_large), 60 requests a minute per key (429 rate_limited with retry_after).

MethodPathWhat it doesSuccessErrors
POST/api/jobsSend a parcel. Body {"task":"echo|read_file|write_file|claude","args":{...}}. The Hub checks it against the key's contract.202 queued or waiting_approval403 refused (the body says why), 401, 413, 422 invalid, 429
GET/api/jobs/:idStatus and result of one of this key's own parcels.200401, 404 not_found (also for another key's parcel), 429

The arguments each task needs: echo takes text; read_file takes path; write_file takes path and content; claude takes prompt and cwd (the folder to work in).

Examples

Send an echo parcel. The key here is fake.

curl -X POST https://<your-hub>/api/jobs \
  -H "Authorization: Bearer mr_live_..." \
  -H "Content-Type: application/json" \
  -d '{"task":"echo","args":{"text":"hello"}}'

HTTP 202
{"id":"p_1000","state":"queued"}

A write the contract says must wait for you:

curl -X POST https://<your-hub>/api/jobs \
  -H "Authorization: Bearer mr_live_..." \
  -H "Content-Type: application/json" \
  -d '{"task":"write_file","args":{"path":"~/notes/todo.md","content":"- buy stamps"}}'

HTTP 202
{"id":"p_1001","state":"waiting_approval"}

A path outside the contract. The parcel is recorded but never reaches the laptop:

curl -X POST https://<your-hub>/api/jobs \
  -H "Authorization: Bearer mr_live_..." \
  -H "Content-Type: application/json" \
  -d '{"task":"read_file","args":{"path":"~/secret/a.txt"}}'

HTTP 403
{"id":"p_1002","state":"refused","reason":"~/secret/a.txt is outside the contract"}

Ask how the first parcel went:

curl https://<your-hub>/api/jobs/p_1000 \
  -H "Authorization: Bearer mr_live_..."

HTTP 200
{"id":"p_1000","state":"done","result":{"echo":"hello"},
 "created_at":1767225600000,"updated_at":1767225600450}

A wrong key:

HTTP 401
{"error":"bad_key"}

Poll GET /api/jobs/:id until state is one of the finished states below. There is no push to clients. Every poll counts toward the 60 requests a minute per key, so poll every few seconds, not every second: a poll every second gets 429 rate_limited after a minute.

Parcel states

StateMeaningFinished?
queuedAccepted. Waiting for the laptop (or for its turn).no
waiting_approvalAllowed, but waits for you to say yes.no
runningSent to the laptop. If the laptop drops, it goes back to queued.no
doneThe laptop finished. result holds the answer.yes
failedThe laptop tried and failed. reason says why.yes
refusedTurned away by the contract, by the laptop's own check, or declined by you.yes
cancelledIts key was revoked before it finished.yes

A state named expired appears in the filter lists, but the Hub does not set it today. An expired contract shows up as 401 bad_key or a refused parcel.

Owner routes

The cookie mr_session comes from signing in. Without it every route here answers 401 signed_out. A POST, PUT or DELETE whose Origin header is another site is 403 bad_origin. Reads are not checked.

Live event stream

The stream sends one message per event, with the event number as its id:

id: 41
data: {"seq":41,"ts":1767225600000,"kind":"job.queued","payload":{"job_id":"p_1000","key_id":"k_1000","task":"echo"}}

It first replays everything after after, then stays open. A : ping comment arrives every 20 seconds to keep it alive. A client that reconnects with a Last-Event-ID header resumes from there. See Events.

The daemon socket

GET /daemon as a WebSocket upgrade, header Authorization: Bearer mrd_.... Without an upgrade request: 426 upgrade_required (unless it is a probe, below). A missing or wrong credential: 401 bad_credential. Only one laptop is connected at a time: a new valid connection replaces the old one. Each message is one JSON text frame.

MessageFromFieldsMeaning
hellodaemonversion, last_seqFirst message. The Hub marks the laptop connected.
welcomeHubserver_seqReply to hello. The Hub then sends queued parcels, one at a time.
jobHubid, task, args, contract, contract_versionDo this. The parcel becomes running.
resultdaemonid, ok, result or errorDone (ok:true) or failed (ok:false).
refusedaemonid, reasonThe laptop's own check said no.
cancelHubidStop this running parcel (its key was revoked).
ping / pongHub / daemonnoneThe Hub pings every 25 seconds. With no pong for 60 seconds, the laptop counts as disconnected.

The Hub closes the socket with code 4001 when you rotate the credential, and 4002 when another connection replaces it. The daemon does not retry after either. After other drops it reconnects with a growing delay, 1 second up to 30.

Checking the credential without connecting

GET /daemon?probe=1 with the header Authorization: Bearer mrd_... and no WebSocket upgrade is a plain check. With the right credential it answers 200 {"ok":true,"connected":true} (or false when no laptop is connected). With any other credential it answers 401 bad_credential. It never replaces the connected laptop, so it is safe to call while the daemon is working. It is what mailroom status uses.

MCP

POST /mcp with Authorization: Bearer mra_.... One JSON-RPC message per request. Scopes, the 15 tools and the limits are on Claude and other apps (MCP).
