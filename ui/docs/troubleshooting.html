Troubleshooting

The things most likely to go wrong, each with what causes it and what to do.

Start with the place that tells you the most: the Laptop page for connection problems, the refused parcel's page for "why was this turned away", and the log file ~/Library/Logs/mailroom-daemon.log for anything about the background service.

The laptop

The app says the laptop is "out to lunch"

Cause. No daemon is connected to the Hub right now. The laptop may be asleep or offline, mailroom may never have been started, or its credential may no longer be accepted. Parcels are not lost: they queue and run in order when it is back.

Fix.

  1. On the laptop run mailroom status. The hub: line tells you what the Hub says: accepted, rejected, unknown (an old Hub) or unreachable.

  2. Not logged in? Run mailroom login. Rejected? The credential was rotated or is wrong: run mailroom login with the current one from the Laptop page.

  3. Start it: mailroom run to try it, or mailroom service install to keep it running (macOS).

  4. Already installed? Run mailroom service status. If it says "not running", read the end of ~/Library/Logs/mailroom-daemon.log for the reason.

mailroom status and mailroom service status are safe: they only ask the Hub and never replace a running daemon. If the Laptop page still flips between connected and away, a second daemon may be using the same credential. See below.

The daemon exits again and again

Cause. The background service restarts the daemon whenever it stops. If it stops right away every time, launchd waits 30 seconds between tries. The usual reasons are a credential the Hub rejects, no saved login ("Not logged in"), or another daemon that took over. A wrong Hub address does not make it exit: it keeps retrying and the log shows "reconnecting".

Fix. Read the last lines of ~/Library/Logs/mailroom-daemon.log. They name the reason. Then fix it (usually mailroom login) and run mailroom service install again. That replaces the running copy at once instead of waiting for the next 30 second retry. To stop the loop while you sort it out, run mailroom service uninstall.

The log says "Replaced by another daemon. Exiting."

Cause. Only one daemon can be connected at a time. A second connection takes over and the first one is told to leave. There is exactly one daemon credential per Hub, so anything that connects with it counts: a second mailroom run, or another machine using the same credential.

The usual trap is running both the background service and a manual mailroom run. They take over from each other. The loser prints "Replaced by another daemon. Exiting." and exits with code 2. Under launchd it comes back about 30 seconds later and takes over again, so the laptop keeps flipping between connected and away.

Fix. Run only one daemon. Stop one of them: run mailroom service uninstall to remove the background service, or stop the manual mailroom run with Ctrl+C. The Hub has one credential, so a second machine cannot be given its own.

The credential was rotated

Cause. Someone (you) pressed "Rotate credential" on the Laptop page. The old credential died at once. The daemon prints "The daemon credential was rotated. Run mailroom login with the new credential." and exits.

Fix. Copy the new credential from the Laptop page (it is shown once), then run mailroom login and mailroom service install. If you lost it, rotate again. Full steps are on The laptop and the daemon.

A claude task fails because claude is not found

Cause. The background service does not get your terminal's PATH. launchd gives it a short one: Node's folder, ~/.local/bin, /opt/homebrew/bin, /usr/local/bin and the system folders. If claude lives somewhere else, a terminal finds it but the service does not. The job fails with an error from the system that it could not start claude.

Fix. Make claude reachable from one of those folders, for example with a link in ~/.local/bin. Then run mailroom service install again, because the PATH is written when you install.

Parcels and keys

A parcel was refused

Cause. The contract said no. The most common reasons: the path is outside the allowed folders, the task is not in the contract, or the daily limit is reached. The daemon can also refuse a path that looks inside but really points outside (a symlink).

Fix. Open Parcels, click the refused parcel and read Why it was refused. It shows what was asked next to what the contract allows. If the request was fine, click Widen the contract and add the folder or task. If not, leave it refused. Nothing reached your laptop either way.

A parcel says "failed"

Cause. The contract allowed it, but the work went wrong on the laptop. Known reasons: a file larger than 2 MB ("file is bigger than 2 MB"), content to write over 200 KB, a result that encodes to more than 2 MB ("result is bigger than 2 MB"), the laptop dropping mid-run on a task that is not safe to repeat ("laptop dropped mid-run; not re-run-safe"), a claude task that ran longer than 5 minutes ("claude timed out"), or claude exiting with an error.

Fix. The parcel page shows the error text. Send a smaller file, or shorten the prompt. The timeout can be changed for a daemon you start yourself with MAILROOM_CLAUDE_TIMEOUT_MS (see The mailroom command).

A key stopped working

Cause. There are three different reasons, and they look different to the client.

The client seesCause
401 bad_keyThe key was revoked, or its contract has expired. A revoked key stops at once.
A refused parcel, reason "daily limit of N reached"The key has used its parcels for today. The count starts again at midnight UTC.
429More than 60 requests in a minute from this key. Polling a parcel counts too, so poll every few seconds, not every second.

Fix. Open Keys and check the status. A revoked key cannot be undone: hand out a new one. For an expired contract, set a later date. For the daily limit, raise it in the contract.

The extension

The extension's settings are stuck on "Checking..."

Cause. The extension asks the Hub for its state and waits at most 8 seconds. After that it stops waiting and tells you what it thinks went wrong, so "Checking..." should not stay. If it does, reload the extension on chrome://extensions.

What the message means:

MessageCause and fix
No answer from the Hub after 8 s. Check the address and your connection.The address is wrong, you are offline, or the Hub is down. Open the address in a normal tab.
Cannot reach the Hub. Is the address right, and is access to it allowed for this extension?Wrong address, or Chrome did not allow access to it. Save the address again and allow it when asked.
Signed out. Sign in on the Hub, then reopen the popup.Open the Hub in a normal tab and sign in. The extension uses that sign-in.

A grey x on the toolbar icon also means signed out, and a grey ? means no answer.

Signing in and deploying

The sign-in page says "Door is locked"

Cause. Five wrong passwords from your address within 15 minutes. While the door is locked even the right password is refused.

Fix. Wait. The page shows a countdown, and the 15 minutes count from the first wrong try. A correct sign-in afterwards clears the count.

Sign-in fails with "The door is stuck", or the Hub answers 500 "misconfigured"

Cause. A new Worker has no password yet. Until the two secrets OWNER_PASSWORD and SESSION_SECRET are set, the Hub refuses every sign-in on purpose (it fails closed), and the sign-in page can only say the door is stuck.

Fix. The secrets can only be set after the Worker exists, so deploy once first, then set them:

npx wrangler secret put OWNER_PASSWORD
npx wrangler secret put SESSION_SECRET

Locally, put both in .dev.vars and restart npm run dev.

Not sure which end is at fault? Open the Laptop page. "Connected" means the laptop side is fine and the problem is in a contract or a key. "Out to lunch" means start with the first question on this page.
