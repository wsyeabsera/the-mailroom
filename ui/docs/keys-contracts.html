Keys and contracts

A key says who is sending. A contract says what that sender may do. Every parcel is measured against the contract before anything runs.

You make a contract first (folders, tasks, a daily limit, an expiry, and which tasks need your yes). Then you make a key and tie it to that contract. The app sends the key with every parcel. The Hub looks up the contract and decides: allow, wait for you, or refuse with a reason. The Hub sends the contract along with every job, and your laptop checks that contract again before it does the work.

Keys

A key is a long secret string that an app sends with each parcel. It looks like this:

mr_live_...

After mr_live_ come 32 random letters and digits. The examples in these docs are never real.

  • Shown once. When you make a key, you see the whole thing one time. Copy it then.
  • Only a hash is stored. The Hub keeps a one-way fingerprint (a SHA-256 hash), not the key. Nobody, including you, can read it back. The admin app lists only the first 12 characters, so you can tell keys apart.
  • One key, one contract. A key is tied to a single contract. To change what an app may do, change the contract (see below) or make a new key.
  • Revoke applies at once. On the key's page, press Revoke key. Its next request gets a 401, and its queued, waiting and running parcels become cancelled.

If you lose a key, you cannot recover it. Revoke it and make a new one. Give each app its own key, so you can revoke one without stopping the others.

A key is not the same as the laptop's credential (mrd_...) or an MCP token (mra_...). Each kind works only for its own job.

Contracts

A contract has these parts:

PartWhat it means
NameA short label, up to 60 characters. Letters, digits, spaces and _ . ( ) - only.
FoldersWhere file work may happen. Each must start with ~/ (your home folder) or /. You must list at least one. ~ or / alone is not accepted, because it would mean anywhere.
TasksWhat the key may ask for. At least one of the four below.
Daily limitA whole number from 1 to 100000: how many parcels per day (UTC) this key may send.
ExpiresA date such as 2026-12-31, or empty for never. A date means the start of that day in UTC: with 2026-12-31 the contract stops working at 00:00 UTC on the 31st, not at the end of it.
CommandsNames the run task may start. Required (at least one) when run is allowed. The laptop decides what each name does.
Needs approvalTasks that wait for you before they run. Only tasks the contract allows can be listed.

The five tasks

TaskWhat it doesPath it needs
echoSends your text straight back. A safe test.none
read_fileReads one file (up to 200 KB).path
write_fileWrites one file (up to 200 KB). Creates folders inside the allowed folder if needed.path
claudeRuns claude -p with your prompt in a folder. Times out after 5 minutes. A job may only ask for tools and turns the contract lists (default: Read, Glob, Grep and 10 turns); with none asked, it gets exactly those.cwd (the folder to work in)
runStarts a named command you registered in ~/.mailroom/commands.json on the laptop (a script, typed arguments, a timeout and a folder). No shell: arguments are passed as plain values. The folder must be inside the contract's folders.none (the laptop's registry sets the folder)

The "daily limit" counts every parcel the key sent since 00:00 UTC except refused ones. Cancelled parcels still count. The laptop does not count it again, so the limit is enforced only by the Hub.

How a parcel is checked

The checks run in this order. The first one that fails ends it.

How paths are judged

  • A path must start with ~/ or /. A relative path such as notes/a.txt is refused.
  • .. is worked out first. ~/notes/../secrets/a.txt becomes ~/secrets/a.txt, which is outside ~/notes, so it is refused. A path that climbs above its root is refused outright.
  • A folder only matches whole names. With the folder ~/notes, the path ~/notes-old/a.txt is outside, because it is a sibling that merely starts with the same letters. ~/notes/a.txt is inside.
  • The laptop looks at real paths. It follows shortcuts (symlinks) to where a file really lives. A symlink inside an allowed folder that points outside it is refused with "resolves outside the contract folders".

Worked examples

Take a contract with folder ~/notes, tasks read_file and write_file, and write_file marked "needs approval".

ParcelResult
read_file ~/notes/todo.txtqueued Allowed. It goes to the laptop.
write_file ~/notes/new.txtwaiting_approval Allowed, but it waits for you.
read_file ~/notes/../.ssh/id_rsarefused ~/notes/../.ssh/id_rsa is outside the contract
read_file ~/notes-old/a.txtrefused ~/notes-old/a.txt is outside the contract
claude in ~/notesrefused task “claude” is not in the contract

Editing a contract

  1. Open Contracts and pick the contract. The page says how many keys use it.
  2. Change what you need. The "In plain words" box on the right reads the contract back, so you can check it says what you mean.
  3. Press Save contract. Mistakes show next to the field and nothing is saved.

The change applies to the next parcel. Parcels already in the system are checked again at these moments:

  • Queued parcels are checked again just before the Hub sends them to the laptop. If the new contract no longer allows one, it becomes refused with the reason.
  • Waiting parcels are checked again when you approve. If they now break the contract, the approval turns into a refusal.
  • Running parcels are not stopped.

Editing a contract never rescues a parcel that was already refused. Send it again after you widen the contract.

Make a contract with folder ~/mailroom-play and the task echo only. Send a read_file parcel and read the refusal reason. Then add read_file to the contract, save, and send it again.

Under the hood: what the Hub records
  • Saving a contract adds a contract.saved event and raises its version number. Each parcel remembers the version it was last checked against.
  • The gateway turns away a key whose contract has expired with a 401 before the check, so the "contract expired" reason appears only for parcels already in the system when the expiry passes.
  • The daemon calls the same check() function on the contract the Hub sent with the job, using its own clock, then resolves real paths. Its home folder replaces ~, which the Hub never expands. This is a second look at the same contract. What protects you against a compromised Hub is the laptop policy file ~/.mailroom/policy.json: the daemon refuses any contract whose folders, tasks or commands go beyond it. Without that file, the daemon trusts the contract the Hub sends.
