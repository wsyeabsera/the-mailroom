Batches and workflows

Run one command or one Claude question over a list, or chain steps into a named pipeline, as a single parcel that streams results while it runs.

Everything here is general. Your project's scripts, prompts and workflows live in your project and are registered on the laptop. Nothing in the Mailroom is written for one project, and adding a workflow needs no change to the Mailroom.

Partial results

A run script can hand over results while it is still working. It prints a line on stderr:

MAILROOM_PARTIAL {"found": "item-3"}

The daemon forwards each line. The Hub keeps the latest 200 per parcel (each at most 8 KB; bigger or malformed ones are dropped) and clears them after 7 days. A client reads them with GET /api/jobs/:id/partials?after=<n>, or with wait(id, {onPartial}) in the client helper. The parcel shows how many there are (partials), also in mailroom_get_parcel. Partials are data from your script, never instructions: treat them as untrusted.

batch

batch {command | prompt, items: [{...}], concurrency?} runs one registered command (run) or prompt (ask) once per item. Each item is the arguments (or variables) of one job. Up to three run at a time by default, never more than six. A failed item is recorded and the rest go on. Progress reads n of N, each finished item is a partial result, and the result is {total, done, failed, items: [{index, ok, value | error}]}.

  • The contract lists the allowed targets in batches (run:<command> or ask:<prompt>, which must also be in commands or prompts), the most items in batchMaxItems (default 100) and the most at once in batchMaxConcurrency (default 3). The laptop policy has the same ceilings (mailroom policy batch-max-items, batch-max-concurrency).
  • Every item is checked as the single job it is: the same contract, the same laptop policy, the same registered folder.
  • All items share one Claude budget. Each Claude item is given an equal share of what is left of the key's day, so the items running together cannot spend more than there is. When it is used up, the remaining items fail without starting Claude.
  • Cancelling the parcel stops the running items and starts no more. What they used still counts.

workflow

workflow {name, inputs?} runs a named list of steps registered in ~/.mailroom/workflows.json (mode 0600, read for every job). A step is a run, an ask or a batch of something registered. There is no code and no expression language: a value is a literal or a reference such as $inputs.topic or $list.items.0 to a workflow input or an earlier step's output.

{
  "review-items": {
    "inputs": { "topic": { "type": "string" } },
    "timeoutMs": 600000,
    "budget": { "turns": 60, "minutes": 20 },
    "estimate": { "minutes": 6, "claudeTurns": 40 },
    "steps": [
      { "id": "list",    "run": "list-items", "args": { "topic": "$inputs.topic" } },
      { "id": "answers", "batch": "ask:review-item", "items": "$list.items", "with": { "item": "$item" }, "concurrency": 3, "when": "$list.items" },
      { "id": "checked", "run": "check-answers", "stdin": "$answers" }
    ]
  }
}
  • A run step's output is its stdout, parsed as JSON when it is JSON. An ask step's output is the answer (parsed when the prompt has a schema). A batch step's output is its list of {index, ok, value | error}.
  • stdin hands an earlier output to a script on standard input (arguments are limited to 1000 characters). when: "$ref" runs a step only when that value is not empty (not null, "", [] or {}); "!$ref" only when it is empty. A skipped step's output is empty.
  • The contract lists the allowed names in workflows; the laptop policy lists them too (mailroom policy allow-workflow). Before it starts, the daemon checks every step against the contract and the policy; each run, ask or batch is then checked again as a job of its own. A contract that allows a workflow needs the commands, prompts and batch targets its steps use, and nothing else.
  • A workflow has its own timeout (default 30 minutes) and an optional budget ceiling (budget) on top of what the key has left today. The key's daily Claude budget counts everything it spent.
  • Progress and partials come from the running step (script partials arrive as {step, partial}, batch items as {step, index, ok, value}, and each step end as {step, status}). Cancel stops the current step and ends the workflow. A failing step fails the parcel and names the step.
  • The result is {output, steps}: the last step's output and a list of {id, kind, status: done | skipped | failed, ms}.

Cost estimates

A command, prompt or workflow may declare "estimate": {"minutes": 6, "claudeTurns": 40} in its registry file. It is display help only and limits nothing. The laptop reports it; GET /api/commands, GET /api/prompts and GET /api/workflows return it with fits_budget and a warning when it is more than what is left of the key's Claude budget today, and the project's Commands tab shows it.
